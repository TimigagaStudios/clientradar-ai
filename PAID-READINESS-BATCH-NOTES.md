# Invoice and lead-record safety batch

Base: main 0a35ef8a31bda66e7ae9cabd5f73ce43fb01d668. Apply all ZIP paths together. No migration, secret, new service, customer email or payment is included.

## Changes

- The invoice page now treats entries as internal records. It does not claim that a record sends an invoice or confirms a payment. It does not invent a project description, price, currency, payment details, tax or terms. Currency remains unverified because this screen does not save or display it. Existing records are not rewritten.
- New amounts and calendar dates receive client-side validation, and creation and manual paid marking require a confirmation. Marking paid is a manual label, not a payment-provider check. Errors and unconfirmed saves are surfaced; the owner should reload and inspect the list before retrying an uncertain creation. Payment status updates and deletes request the affected row and warn on zero rows. This does not replace database-side validation, authorization or an accounting system.
- The print action produces an escaped, simple internal record without private notes, external images or scripts. It is not a complete or legal invoice or a verified receipt. The browser's print dialog, not the app, provides any PDF save option. User/lead text is escaped before insertion in print HTML. Full invoice design and legal/tax requirements remain to be decided and tested.
- Single-lead delete, all-leads reset and duplicate merge now check for linked invoice records before touching child records, and recheck immediately before deleting leads. If linked records are found or the check cannot be performed, deletion is blocked instead of automatically deleting or detaching invoices. A PostgreSQL undefined-table error is the only missing-table exception. Existing invoice records and links are not changed by this guard.
- These existing multi-query operations are NOT transactions: other related records may already change if a later step fails, and a concurrent invoice insert can race the final check. Database constraints and a reviewed atomic server/database design are still necessary for robust protection. Other delete paths, integrations and database behavior are not guaranteed by this change. Never test destructive operations against production data. Duplicate merge can move only listed relationships and can leave partial work. Its dialog no longer promises everything moves, and failures remain visible after reload. Lead cards and details now show the reason a delete was blocked; Settings warns reset can be partial.

## Verification and limitations

29 offline suites passed, including pure printable-record escaping and input tests plus mocked single delete, reset and merge invoice preflight. Targeted server TypeScript passed; full-client diagnostics match the existing 17 baseline errors after line-number normalization. Synthetic actual-component Chromium and WebKit invoice checks passed at 320, 390, 768 and 1280 pixels using mock Supabase and synthetic records, covering creation confirmation, manual paid confirmation, data display and no unintended write on cancel. No physical-device, live database, payment-provider, RLS/permission, production print-to-PDF, concurrent transaction or complete accessibility tests were conducted.

Client invoice operations continue to use the existing direct Supabase client and existing policies, which were not audited or verified in this batch. The guard is not a substitute for backup or database-enforced protection. Local production Vite build not verified; require a successful Vercel branch build. Previous PR #14 matched all 9 ZIP paths and GitHub reported Vercel deployment success, not independent live functionality. No real records were used or modified in the tests. Existing outreach approvals were not changed.
